## 2. Описание продукта

### Потребность

Проверка задания ЕГЭ №13 требует не только знания правильного ответа. Эксперт должен понять ход решения ученика, проверить преобразования, общий набор корней и отбор корней на указанном отрезке, после чего выставить 0, 1 или 2 балла по критериям.

При обычной работе преподаватель вручную:

1. читает рукописное решение;
2. восстанавливает математическую запись;
3. решает задачу независимо;
4. сравнивает решение ученика с эталоном;
5. проверяет отбор корней;
6. формулирует комментарий.

Это повторяемая работа, которую можно частично автоматизировать.

### Решение

**MathCheck AI** — локальная мультиагентная система, которая принимает одну или несколько фотографий одной работы ЕГЭ №13 и формирует предварительный экспертный отчёт.

Ключевая особенность — система не доверяет OCR напрямую. После Vision-распознавания пользователь подтверждает:

- исходное уравнение;
- интервал пункта б;
- полный текст решения ученика.

Только после этого запускается математическая проверка.

Итог системы:

- балл 0–2;
- краткий итог по пунктам а) и б);
- найденные ошибки;
- правильный ответ;
- проверенный отбор корней;
- время выполнения каждого этапа.

Система работает локально через Ollama, поэтому фотографии учеников не требуется отправлять во внешний LLM API.

## 3. Ход работы

### Этап 1. Проектирование

На первом этапе был определён MVP: поддерживать только ЕГЭ №13 и довести один тип задания до устойчивого end-to-end сценария.

Ключевые решения:

- разделить чтение фото и математическое оценивание;
- использовать четыре специализированных агента вместо одного большого prompt;
- добавить обязательное подтверждение OCR человеком;
- проверять LLM-эталон детерминированными математическими tools;
- хранить общий state в LangGraph.

### Этап 2. Реализация ядра

Реализованы:

- Vision Agent;
- Solver Agent;
- Grader Agent;
- Reviewer Agent;
- LangGraph graph;
- parser школьной математической записи;
- reference verifier на Python/SymPy;
- rubric для выставления балла;
- генерация пользовательского отчёта.

### Этап 3. Интерфейс и интеграция

Добавлены:

- загрузка от 1 до 8 фотографий;
- объединение нескольких страниц в один Vision-вызов;
- OCR editor;
- preflight перед запуском Solver;
- отображение прогресса этапов;
- сохранение истории в SQLite;
- Docker-конфигурация;
- локальный Ollama runtime.

### Этап 4. Тестирование и документация

Подготовлены:

- unit-тесты;
- экспертный eval-набор по №13;
- отдельные Vision и grading benchmark;

- README и инструкция запуска.

### LangGraph граф

Поток в MathCheck AI в основном **последовательный**, а не fan-out. Это осознанное решение: следующий этап зависит от результата предыдущего.

```text
START
  │
  ▼
[input / photos]
  │
  ▼
[Vision Agent]
  │
  ▼
[Human confirmation]
  │
  ▼
[Preflight]
  │
  ├── invalid ─────► обратно в OCR editor
  │
  ▼ valid
[Solver Agent]
  │
  ▼
[Reference Verifier]
  │
  ▼
[Grader Agent]
  │
  ▼
[Reviewer Agent]
  │
  ▼
[Report Builder]
  │
 END
```

### Почему multi-agent, а не один prompt

Один универсальный LLM-вызов одновременно должен был бы читать фото, решать задачу, проверять ученика и выставлять балл. Тогда невозможно понять, на каком этапе возникла ошибка.

В текущей архитектуре ответственность разделена:

- **Vision Agent** — только транскрипция изображения;
- **Solver Agent** — независимое решение подтверждённой задачи;
- **Grader Agent** — сопоставление решения ученика с эталоном и критериями;
- **Reviewer Agent** — аудит непротиворечивости итогового результата.

Детерминированные операции не оформлены как дополнительные агенты. Preflight, SymPy verifier, parser, rubric, report builder и persistence — обычные tools/components.

## 5. Выбор стека и аргументы

### LangGraph vs альтернативы

| Фреймворк | Плюсы | Минусы | Решение |
|---|---|---|---|
| **LangGraph** | Явный state graph, контроль переходов, удобно для human-in-the-loop | Дополнительная сложность по сравнению с обычным Python pipeline | **Выбран** |
| CrewAI | Простой role-based API | Меньше контроля над строгим математическим flow | Не выбран |
| AutoGen | Подходит для диалоговых агентов | Избыточен для фиксированной последовательности | Не выбран |
| Самописный pipeline | Полный контроль | Нужно самостоятельно реализовывать state/routing | Не выбран |

**Почему выбран LangGraph:** задача естественно представляется как граф состояний. Особенно важны явная граница human confirmation, возврат пользователя в редактор при preflight error и разделение LLM/детерминированных узлов.

### Ollama vs альтернативы

| Runtime | Плюсы | Минусы |
|---|---|---|
| **Ollama** | Локально, бесплатный inference, удобный HTTP API, Vision models | Сильно зависит от локального железа |
| OpenAI API | Высокая скорость и качество | Внешнее облако и стоимость |
| vLLM | Высокая производительность | Требует более серьёзного GPU и настройки |
| llama.cpp напрямую | Легковесный runtime | Нужно больше собственной интеграции |

**Почему Ollama:** учебный проект должен быть воспроизводим локально; также это позволяет не отправлять ученические работы наружу.

### FastAPI vs альтернативы

FastAPI выбран для REST API из-за простого запуска, Pydantic-валидации и встроенного Swagger UI.

### SymPy

SymPy используется не как LLM, а как независимый математический инструмент. Он проверяет выражения, семейства решений и корни на интервале.

Это принципиально: правильный ответ не должен зависеть только от генеративной модели.

### Docker и venv

Основной локальный сценарий работает через `venv`, а Docker используется как воспроизводимый вариант развёртывания Agent App. Ollama на macOS можно оставлять нативно на host, чтобы использовать локальное ускорение.

### Persistence

Для истории проверок используется SQLite. Для LLM telemetry и slow-call alerts используются JSONL-логи.

## 6. Проблемы и решения

### Проблема 1. OCR может менять математику ученика

**Симптом:** Vision иногда неверно считывает знак, степень, параметр или часть формулы.

**Риск:** Grader будет проверять не то, что написал ученик.

**Решение:** введена обязательная human confirmation boundary. До подтверждения transcript математические агенты не запускаются.

---

### Проблема 2. Неоднозначная школьная запись

**Симптом:** записи вроде `sin x (x+π)`, `2πn`, `3πm/4`, индексы параметров и OCR-варианты могут быть разобраны неоднозначно.

**Решение:** реализован отдельный parser и deterministic preflight. Если запись неоднозначна, система не угадывает смысл, а требует уточнения.

---

### Проблема 3. LLM может построить неверный эталон

**Симптом:** Solver способен вернуть правдоподобный, но математически неверный набор корней.

**Решение:** после Solver запускается отдельный deterministic reference verifier на Python/SymPy. Grader получает только подтверждённый verified reference.

---

### Проблема 4. Большая latency локальных моделей

**Симптом:** один Vision-вызов на рукописной математике может занимать несколько минут.

**Решения:**

- несколько фотографий объединяются в один Vision-вызов;
- убрана дополнительная Vision-проверка нарисованной учеником окружности;
- для каждого этапа измеряется отдельное время;
- Grader и Reviewer выполняются single-pass без скрытых retry-циклов.

---

### Проблема 5. Невалидный JSON и длинная генерация Vision

**Симптом:** локальная multimodal-модель могла после полезного OCR продолжать генерировать пустые строки или оборвать JSON.

**Решение:** введён структурированный response schema, лимит генерации и строгая проверка финального JSON. Частичный ответ не считается успешным.

---

### Проблема 6. Незавершённый Ollama stream

**Симптом:** при тестировании отдельных Vision-моделей встречался `OLLAMA_STREAM_INCOMPLETE` — HTTP stream закрывался до финального `done`.

**Решение:** transport отделён от логики агентов; незавершённый stream фиксируется как технический сбой, а не как корректный OCR результат. Для рабочего MVP оставлена стабильная конфигурация основной модели.

---

### Проблема 7. Ошибка в окружности увеличивала latency и путала критерии

Проверка нарисованной учеником тригонометрической окружности требовала ещё одного Vision-прохода и значительно увеличивала время.

В текущем MVP окружность ученика **не оценивается**. Пункт б проверяется по подтверждённому тексту и выбранным корням. Эталонная окружность может строиться детерминированно в отчёте.

## 7. Система оценки (Evals)

### Что оцениваем

В проекте специально разделены два типа качества:

1. насколько Vision-модель умеет читать фотографию;
2. насколько grading-система правильно выставляет балл после предусмотренного human confirmation.

### Dataset

Подготовлен экспертно размеченный набор из 12 работ ЕГЭ №13:

- 4 работы на 2 балла;
- 4 работы на 1 балл;
- 4 работы на 0 баллов.

Для каждого кейса хранятся:

- фотография;
- условие;
- интервал;
- ручная транскрипция;
- экспертный балл;
- экспертный комментарий;
- ожидаемые ключевые шаги;
- ожидаемые ошибки.

### SYSTEM benchmark

Flow:

```text
Human-confirmed transcript
        ↓
Solver
        ↓
Reference Verifier
        ↓
Grader
        ↓
Reviewer
        ↓
Final score vs expert score
```

Результат на 10 кейсах, `qwen3-vl:4b-instruct`:

| Метрика | Значение |
|---|---:|
| Cases | 10 |
| Scored cases | 10 |
| Score accuracy | **0.90** |
| Mean absolute score error | **0.10** |
| Reference success rate | **1.00** |
| Manual review rate | 0.10 |
| Manual review match rate | 0.70 |
| False error rate on expert=2 | 0.00 |
| Positive score rate on expert=0 | 0.00 |
| Average total time | 166.97 s |
| Average Solver | 41.89 s |
| Average Reference Verifier | 0.38 s |
| Average Grader | 100.10 s |
| Average Reviewer | 18.15 s |
| Diagram Vision | 0.00 s |

По кейсам:

```text
13.1.1  score 2/2
13.1.2  score 2/1
13.1.4  score 0/0
13.2.1  score 2/2
13.2.2  score 1/1
13.2.4  score 0/0
13.3.1  score 2/2
13.3.3  score 1/1
13.3.4  score 0/0
13.4.1  score 2/2
```

Единственное несовпадение — `13.1.2`. Экспертный балл учитывает ошибку в визуальном отборе по окружности, а текущий MVP намеренно не оценивает нарисованную учеником окружность.

### VISION benchmark

Flow:

```text
Photo
  ↓
Vision Agent
  ↓
Raw OCR
  ↓
comparison with manual transcript
```

Результат `qwen3-vl:4b-instruct` на 10 кейсах:

| Метрика | Значение |
|---|---:|
| Vision success rate | **1.00** |
| Valid JSON rate | **1.00** |
| Mean OCR similarity | **0.268** |
| Human correction rate | **1.00** |
| Average Vision time | **286.32 s** |

`human_correction_rate = 1.0` означает, что на всех 10 работах сырой OCR отличался от ручной ground-truth транскрипции хотя бы в одном фрагменте. Именно поэтому human confirmation является частью архитектуры, а не необязательным UI-шагом.

### Запуск eval

```bash
python evals/prepare_ege13_images.py
python evals/run_ege13_benchmark.py --models qwen3-vl:4b-instruct --limit 10
```

Для Vision-only сравнения:


## 8. Observability

Observability встроена на нескольких уровнях.

### Stage timings

Отдельно измеряются:

- Vision;
- preflight;
- Solver;
- reference verifier;
- Grader;
- Reviewer;
- report builder;
- persistence.

### LLM telemetry

Для локальных LLM фиксируются:

- model name;
- wall time;
- prompt tokens;
- output tokens;
- generation time;
- load time;
- скорость генерации;
- done reason;
- transport status;
- errors/timeouts.

### Structured logging

Локальные события сохраняются в JSONL. Для медленных вызовов формируется отдельный slow-call alert.

Пример структуры события:

```json
{
  "event": "llm_call_completed",
  "agent": "grader",
  "model": "qwen3-vl:4b-instruct",
  "duration_seconds": 96.4,
  "status": "ok"
}
```

### Progress UI

Frontend может получать текущий этап проверки и elapsed time, поэтому пользователь видит, что система не зависла, а выполняет конкретный агент.

## 11. Пример работы системы

### Шаг 1. Загрузка

Пользователь загружает фотографию или несколько страниц одного решения.

### Шаг 2. Vision

Vision Agent возвращает черновую транскрипцию решения.

### Шаг 3. Подтверждение

Пользователь видит фотографию рядом с распознанным текстом и подтверждает/исправляет:

```text
Уравнение
Интервал пункта б
Решение ученика
```

### Шаг 4. Проверка

Solver строит независимый эталон, reference verifier проверяет его математически, Grader сопоставляет решение ученика с эталоном и критериями, Reviewer выполняет финальный consistency audit.

### Шаг 5. Итоговый отчёт

Пример содержимого:

```text
Результат: 1/2

Пункт а): выполнен верно.
Пункт б): допущена ошибка при отборе корней на заданном отрезке.

Комментарий:
Общее решение уравнения получено корректно, но в итоговый набор попал корень,
не принадлежащий указанному промежутку.

Правильные корни на отрезке: ...
```

В отчёте дополнительно отображается время этапов.

## Итог

В результате разработан рабочий MVP локальной мультиагентной системы для предварительной проверки ЕГЭ №13.

Основные результаты:

- реализован end-to-end сценарий от фотографии до итогового отчёта;
- реализованы четыре специализированных агента;
- ошибки OCR отделены от математического grading через human confirmation;
- LLM-эталон дополнительно проверяется детерминированным SymPy verifier;
- grading-система на измеренном наборе из 10 работ совпала с экспертным баллом в 90% случаев;
- reference verifier успешно отработал на всех 10 кейсах;
- реализованы тесты, benchmark, Docker, C4 и Sequence Diagram;
- система полностью может работать локально через Ollama.

Главное ограничение текущего MVP — область применения ограничена заданием ЕГЭ №13, а качество Vision OCR на рукописной математике требует обязательного подтверждения человеком. При расширении проекта следующим шагом может стать поддержка других заданий второй части ЕГЭ и дальнейшая оптимизация local inference.
