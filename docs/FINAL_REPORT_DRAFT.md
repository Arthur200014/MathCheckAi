# MathCheck AI — итоговый отчёт по проекту

## 1. Аннотация

MathCheck AI — локальная мультиагентная система предварительной проверки письменного решения задания ЕГЭ №13 по фотографии. Система принимает одну или несколько фотографий одной работы, выполняет Vision-распознавание, показывает результат человеку для обязательного подтверждения, после чего запускает последовательность агентов и детерминированных проверок. Итогом работы является предварительный экспертный отчёт с баллом, кратким разбором пунктов а) и б), конкретными замечаниями по математическим ошибкам, правильным ответом и временем выполнения этапов.

Основная идея проекта — разделить задачу на несколько специализированных компонентов: Vision Agent отвечает только за чтение фотографии, Solver Agent независимо строит эталонное решение, Grader Agent сопоставляет подтверждённую работу ученика с эталоном и критериями, Reviewer Agent проверяет непротиворечивость результата. Между LLM-агентами используются детерминированные проверки на Python и SymPy.

Текущий MVP ограничен заданием ЕГЭ №13. Важное проектное решение — обязательное human-in-the-loop подтверждение OCR перед математической проверкой. Это позволяет не смешивать ошибки распознавания изображения с ошибками собственно оценивания решения.

---

## 2. Постановка задачи

### 2.1. Проблема

Проверка развёрнутых решений ЕГЭ требует не только получения правильного ответа, но и анализа хода решения: нужно понимать, какие преобразования сделал ученик, где возникла математическая ошибка, выполнены ли оба пункта задания и насколько результат соответствует критериям.

Если использовать одну LLM для всего процесса сразу, возникают несколько проблем:

- ошибка распознавания фотографии может быть ошибочно принята за ошибку ученика;
- модель может «исправить» написанное учеником и оценивать уже не исходную работу;
- генеративная модель может выдать правдоподобное, но математически неверное эталонное решение;
- становится сложно понять, на каком этапе произошла ошибка;
- длинный промпт одновременно с OCR, решением и оцениванием ухудшает устойчивость локальной модели.

### 2.2. Цель

Цель проекта — реализовать локальную agentic-систему, которая:

1. принимает фотографии решения задания ЕГЭ №13;
2. распознаёт условие и решение ученика;
3. требует ручного подтверждения распознанного текста;
4. строит независимый математический эталон;
5. проверяет эталон детерминированными средствами;
6. оценивает работу ученика по критериям;
7. выполняет дополнительный аудит результата;
8. формирует понятный отчёт преподавателю;
9. измеряет качество и время работы отдельных этапов.

### 2.3. Ограничения MVP

В текущей версии:

- поддерживается только ЕГЭ №13;
- OCR всегда подтверждается человеком;
- тригонометрическая окружность ученика не проверяется отдельным Vision-проходом;
- эталонная окружность при необходимости строится детерминированно;
- система является инструментом предварительной проверки, а не заменой официального эксперта ЕГЭ.

## 3. Архитектура системы

Текущий runtime-поток:

```text
1–8 фото одной работы
        ↓
Multi-photo input
        ↓
Vision Agent
        ↓
Human OCR editor
        ↓
Deterministic preflight
        ↓
Solver Agent
        ↓
SymPy / reference verifier
        ↓
Grader Agent
        ↓
Reviewer Agent
        ↓
Deterministic report builder
        ↓
SQLite / итоговый отчёт
```

Для одной фотографии Vision получает исходные байты изображения. Если работа состоит из нескольких фотографий, сервер объединяет страницы в один упорядоченный лист и выполняет один Vision-вызов вместо нескольких последовательных запросов.

После Vision пользователь видит исходное изображение и редактируемые поля:

- исходное уравнение;
- интервал пункта б;
- полный текст решения ученика.

До подтверждения этих данных Solver, Grader и Reviewer не запускаются.

### 3.1. Почему используется LangGraph

LangGraph используется как оркестратор последовательности агентов и общего состояния проверки. В `ReviewState` хранятся подтверждённые данные, промежуточные результаты и техническая информация.

Для данного MVP не вводился отдельный Supervisor Agent. Поток заранее известен и должен быть максимально прозрачным и воспроизводимым. Поэтому фиксированный граф оказался проще для аудита, чем динамическое планирование следующего шага отдельной LLM.

## 4. Компоненты и агенты

### 4.1. Vision Agent

Vision Agent получает изображение и выполняет буквальную транскрипцию. Его задача — переписать реально видимые данные, не решая задачу и не исправляя ученика.

Результат Vision является только черновиком. Он не используется напрямую для выставления балла.

Основные требования:

- сохранять порядок строк;
- не исправлять математические ошибки;
- не восстанавливать отсутствующий текст по памяти;
- отдельно выделять условие и решение ученика;
- отмечать сомнительные места;
- возвращать структурированный JSON.

### 4.2. Human confirmation

Human confirmation — принципиальная граница системы. После него источником истины становятся только:

- `confirmed_task_equation`;
- `confirmed_interval`;
- `confirmed_transcript`.

Это защищает grading-часть от ошибок Vision. Пользователь может исправить OCR до запуска математической проверки.

### 4.3. Deterministic preflight

Перед Solver выполняется детерминированная проверка структуры входа.

Preflight отлавливает, например:

- неоднозначные OCR-конструкции;
- повреждённые скобки;
- некорректный интервал;
- структурно неполные данные.

Если вход неоднозначен, система не пытается угадывать смысл и возвращает пользователя в редактор.

### 4.4. Solver Agent

Solver Agent независимо решает подтверждённое задание. Он не использует решение ученика как источник правильного ответа.

На выходе формируется компактная машинная спецификация:

- переменная;
- семейства общего решения;
- интервал;
- выбранные корни пункта б;
- confidence.

### 4.5. Reference verifier / SymPy

Результат Solver не принимается без проверки. Отдельный детерминированный модуль проверяет выражения, семейства корней и корни на интервале.

Для этого используются Python и SymPy. Это снижает риск генеративной ошибки LLM в эталонном решении.

### 4.6. Grader Agent

Grader получает:

- подтверждённый текст ученика;
- проверенный эталон;
- профиль задания;
- критерии оценивания.

Он определяет характер ошибок и формирует draft результата. При этом финальная логика балла №13 дополнительно контролируется детерминированным rubric-модулем.

### 4.7. Reviewer Agent

Reviewer выполняет один дополнительный проход и проверяет непротиворечивость вывода Grader. Он может добавить advisory или запрос ручной проверки, но не должен незаметно заменять детерминированный итоговый балл.

## 6. Работа с локальными LLM

В проекте LLM вызываются через Ollama. Используется потоковая NDJSON-передача ответа. Транспорт различает несколько типов проблем:

- ошибка подключения;
- отсутствие данных в потоке;
- превышение общего времени;
- незавершённый stream;
- невалидный JSON.

Частичный или оборванный JSON не принимается как корректный ответ.

Для агентов используются структурированные схемы ответа. Это особенно важно для локальных моделей, потому что свободная генерация большого JSON оказалась менее стабильной.

## 7. Методика eval

### 7.1. Набор данных

Для проверки подготовлен экспертно размеченный набор работ ЕГЭ №13. Полный dataset содержит 12 случаев:

- 4 работы на 2 балла;
- 4 работы на 1 балл;
- 4 работы на 0 баллов.

В основном измеренном прогоне использовались первые 10 работ.

Для каждого кейса хранятся:

- изображение работы;
- условие и интервал;
- ручная транскрипция;
- экспертный балл;
- экспертный комментарий;
- ожидаемые ключевые шаги;
- ожидаемые ошибки.

### 7.2. Почему Vision и grading измеряются отдельно

Реальный продукт содержит обязательную ручную проверку OCR. Поэтому eval разделён на две независимые части.

**Vision benchmark:**

```text
Фото → Vision Agent → сравнение OCR с ручной транскрипцией
```

**System benchmark:**

```text
Подтверждённая человеком транскрипция
→ Solver
→ reference verifier
→ Grader
→ Reviewer
→ сравнение итогового балла с экспертом
```

Такой подход позволяет отличить плохое распознавание изображения от ошибки самой системы оценивания.

### 7.3. Метрики

Использовались:

- `score_accuracy` — точное совпадение итогового балла с экспертом;
- `mean_abs_score_error` — средняя абсолютная ошибка балла;
- `reference_success_rate`;
- `manual_review_rate`;
- `manual_review_match_rate`;
- `vision_success_rate`;
- `valid_json_rate`;
- `mean_vision_similarity`;
- `human_correction_rate`;
- latency отдельных агентов и общего процесса.

## 8. Реальные результаты

### 8.1. Проверка grading-системы

На 10 экспертно размеченных работах для `qwen3-vl:4b-instruct` были получены следующие результаты:

| Метрика | Значение |
|---|---:|
| Cases | 10 |
| Scored cases | 10 |
| Score accuracy | 0.90 |
| Mean absolute score error | 0.10 |
| Reference success rate | 1.00 |
| Manual review rate | 0.10 |
| Manual review match rate | 0.70 |
| False error rate on expert=2 | 0.00 |
| Positive score rate on expert=0 | 0.00 |
| Avg total time | 166.97 s |
| Avg Solver time | 41.89 s |
| Avg reference verifier time | 0.38 s |
| Avg Grader time | 100.10 s |
| Avg Reviewer time | 18.15 s |
| Avg diagram time | 0.00 s |

Итоговый балл совпал с экспертным в 9 из 10 случаев.

Единственное расхождение произошло на кейсе `13.1.2`: система поставила 2 балла, а эксперт — 1. Этот кейс связан с ошибкой в визуальном отборе на тригонометрической окружности. Проверка нарисованной учеником окружности намеренно исключена из текущего MVP, поэтому данное расхождение рассматривается как известное ограничение scope, а не как скрытая подстройка системы под benchmark.

### 8.2. Vision для основной модели

Для `qwen3-vl:4b-instruct` на 10 фотографиях:

| Метрика | Значение |
|---|---:|
| Vision success rate | 1.00 |
| Valid JSON rate | 1.00 |
| Mean OCR similarity | 0.268 |
| Human correction rate | 1.00 |
| Avg Vision time | 286.32 s |

Полученный результат показывает, что модель технически стабильно возвращает структурированный ответ, но качество буквального OCR рукописной математики остаётся недостаточным для автоматического доверия без человека. Это подтверждает необходимость выбранной human-in-the-loop архитектуры.

### 8.3. Наблюдения по альтернативным моделям

При локальных прогонах `qwen2.5vl:7b` и варианта `qwen3-vl:4b` были зафиксированы незавершённые Vision-stream ответы (`OLLAMA_STREAM_INCOMPLETE`). После первого тяжёлого Vision-запроса последующие запросы завершались почти сразу без финального `done`-сообщения.

Эти запуски не использовались для расчёта качества OCR как полноценные успешные benchmark-результаты. Они рассматриваются как экспериментальное наблюдение о стабильности локального runtime на целевой машине.

## 9. Интерпретация результатов

Главный результат проекта — grading-часть системы показывает высокое совпадение с экспертной оценкой после предусмотренного ручного подтверждения OCR.

90% точного совпадения балла на выбранных 10 работах означает, что разделение на независимый Solver, deterministic verifier и Grader работает существенно надёжнее, чем схема «одна модель сразу читает, решает и ставит балл».

При этом Vision остаётся наиболее слабым и медленным звеном. Средняя похожесть OCR 0.268 и необходимость коррекции на всех 10 работах показывают, что полностью автоматический режим для рукописной математики на локальной 4B-модели пока нецелесообразен.

Из этого следует важный архитектурный вывод: обязательное ручное подтверждение между Vision и grading является не временным обходным решением, а необходимым механизмом надёжности текущего MVP.

## 10. Надёжность и observability

Система измеряет время отдельных этапов:

- Vision;
- preflight;
- Solver;
- reference verifier;
- Grader;
- Reviewer;
- report builder;
- persistence.

LLM-вызовы логируются локально. Для медленных вызовов может формироваться alert. Такой подход позволяет определить, является ли проблема ошибкой OCR, генерации, symbolic verifier или runtime Ollama.

Для воспроизводимости benchmark сохраняет результаты в нескольких форматах:

- JSON — полный машинный результат;
- CSV — табличный анализ;
- Markdown — человекочитаемая сводка.

## 12. Ограничения

Основные ограничения текущей реализации:

1. Поддерживается только ЕГЭ №13.
2. Рукописный OCR локальной Vision-модели требует ручной коррекции.
3. Локальный inference работает медленно на CPU/GPU ноутбука по сравнению с облачными моделями.
4. Некоторые альтернативные Vision-модели нестабильно работают через локальный Ollama runtime на целевой машине.
5. Нарисованная учеником тригонометрическая окружность в MVP не оценивается.
6. Benchmark пока сравнительно небольшой и содержит 12 подготовленных кейсов.
7. Система не является официальным экспертом ЕГЭ и предназначена для предварительной проверки.

## 14. Вывод

В проекте реализована локальная мультиагентная система проверки письменного решения ЕГЭ №13. Архитектура разделяет распознавание фотографии, построение эталона, математическую верификацию и оценивание ученика.

Ключевыми решениями стали:

- human-in-the-loop после Vision;
- независимый Solver;
- deterministic/SymPy verifier;
- source-lock для текста ученика;
- детерминированная логика итогового балла;
- отдельный Reviewer;
- измерение latency каждого этапа.

На измеренном наборе из 10 работ система после подтверждения OCR воспроизвела экспертный балл в 90% случаев. При этом Vision показал, что распознавание рукописной математики остаётся основной зоной риска, поэтому ручное подтверждение OCR является обоснованной частью архитектуры.

В результате получился не просто чат-бот, который «просит LLM проверить работу», а воспроизводимый agentic pipeline с явными ролями компонентов, детерминированными математическими инструментами, human-in-the-loop границей, тестами и eval-метриками.

## 15. Краткие тезисы для защиты

**Что делает проект?**  
Принимает фото решения №13, распознаёт текст, даёт человеку его подтвердить, независимо решает задачу, проверяет эталон и выставляет предварительный балл с комментариями.

**Почему несколько агентов?**  
Чтобы разделить разные типы задач и ошибок. Vision не должен оценивать, Solver не должен видеть ответ ученика как источник эталона, Grader не должен сам придумывать правильное решение.

**Зачем human confirmation?**  
Потому что OCR рукописной математики несовершенен. Ошибка распознавания не должна становиться «ошибкой ученика».

**Зачем SymPy, если уже есть LLM?**  
LLM предлагает решение, а deterministic verifier проверяет математические выражения и корни. Это уменьшает риск hallucination.

**Почему LangGraph?**  
Он задаёт явный stateful pipeline агентов, условия переходов и позволяет контролировать, какие данные получает каждый этап.

**Главный результат eval?**  
На 10 экспертно размеченных работах grading-система после human confirmation совпала с экспертом в 90% случаев.

**Главное ограничение?**  
Vision OCR локальной 4B-модели пока требует ручной коррекции и работает медленно.

**Почему не проверяется нарисованная окружность?**  
Отдельный Vision-проход по рисунку сильно увеличивал latency и нестабильность, поэтому в текущем MVP рисунок исключён из scoring scope, а эталонная окружность строится детерминированно.
