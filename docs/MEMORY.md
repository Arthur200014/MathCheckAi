# Память MathCheck AI

## Зачем здесь вообще память

У проекта есть три разных типа данных, и их не надо смешивать.

1. Данные одной текущей проверки.
2. История прошлых проверок ученика.
3. Постоянные правила проекта: критерии, skills и служебные инструкции.

Для каждого типа выбран свой способ хранения.

## Краткосрочная память

Краткосрочная память живёт внутри одного запуска LangGraph.

Основной объект - `ReviewState`. В нём по ходу flow появляются:

- исходное фото;
- OCR;
- подтверждённый текст;
- условие;
- результат Solver;
- результат verifier;
- данные Grader;
- решение Reviewer;
- итоговый отчёт;
- timings и warnings.

После первого Vision-прохода flow специально останавливается для подтверждения человеком. Данные незавершённой проверки сохраняются отдельно, чтобы после подтверждения продолжить тот же сценарий, а не начинать всё заново.

## Долгосрочная память

Для истории используется SQLite.

В таблице `reviews` сохраняются:

- `review_id`;
- `student_id`;
- тип задания;
- итоговый балл;
- статус;
- класс ошибки;
- краткий комментарий;
- полный безопасный JSON проверки;
- дата сохранения.

По `student_id` можно получить последние проверки ученика. Для текущего проекта этого достаточно, потому что данные хорошо структурированы.

## Постоянные знания системы

Критерии и правила не хранятся в памяти диалога. Они лежат в репозитории и версионируются вместе с кодом.

Примеры:

- `criteria/task_13.md`;
- `criteria/task_13_rubric.json`;
- `skills/task_13/solve.md`;
- `skills/task_13/grade.md`;
- `knowledge/EXPERT_RULES_13.md`;
- `knowledge/SOUL.md`.

Это удобно, потому что изменение критерия видно в Git и его можно проверить отдельно от модели.

## Почему не обычный RAG

Обычный RAG полезен, когда нужно искать похожие куски в большом неструктурированном наборе документов.

У MathCheck AI другая задача. Например, вопрос "какой балл был у ученика в последней проверке?" лучше решается точным SQL-запросом. Семантический поиск здесь не даёт пользы и может вернуть похожую, но не ту запись.

Критерии №13 тоже небольшие. Они заранее известны и лежат в репозитории. Для них не нужен vector database.

Поэтому classical RAG не выбран как основная память.

## Какие варианты рассматривались

| Вариант | Что умеет | Почему не выбран сейчас |
|---|---|---|
| SQLite | Точные структурированные записи и история | Выбран для MVP |
| Vector RAG | Поиск похожего текста по embeddings | Для score/history точный SQL лучше |
| Graphiti | Временной граф фактов и связей | Слишком сложно для простой истории проверок |
| PageIndex | Навигация по большим документам через иерархию | Корпус проекта маленький |
| SuperMemory | Общая персональная база знаний | Лишняя внешняя прослойка для MVP |
| Cognee | Векторный и графовый слой памяти | Больше инфраструктуры, чем нужно |
| Letta | Агент с изменяемыми блоками памяти | Нам не нужно, чтобы агент сам переписывал свою память |
| LangMem | Долгая память для LangGraph и извлечение фактов | Может пригодиться при персонализации, сейчас не требуется |
| memU | Файловая иерархическая память | Для небольшого количества структурированных review не нужна |
| Mem0 | Память пользователя, сессии и агента | Для нашей истории SQL проще и прозрачнее |
| LlamaIndex | Ingestion и retrieval по разным источникам | Полезен при большом наборе документов, которого сейчас нет |
| Zep | История диалогов и semantic retrieval | Проект не является долгим чат-ассистентом |
| RAGFlow | Большой document/RAG pipeline | Избыточен для одной экзаменационной задачи |

## Недостатки нашего выбора

SQLite тоже не идеален.

- Нет семантического поиска по длинным комментариям.
- Нет автоматического объединения похожих ошибок ученика в одну тему.
- Нет графа связей между темами и ошибками.
- При большом количестве разных заданий схема данных станет сложнее.

Для текущего MVP это приемлемо. Главное преимущество - результат легко проверить и объяснить.

## Что можно улучшить позже

Если система будет хранить тысячи работ по разным темам, можно оставить SQLite как источник точных фактов и добавить второй слой только для поиска по тексту.

Например:

```text
SQLite
  -> точные баллы, даты, статусы

Graphiti или LangMem
  -> повторяющиеся ошибки, связи между темами, персональный контекст
```

То есть advanced memory может появиться как дополнение, а не как замена структурированным данным.
