# Подготовка к защите

Ниже короткие ответы на вопросы, которые прямо указаны в ТЗ или логично следуют из проекта.

## Что такое LLM

LLM - большая языковая модель. Она получает последовательность токенов и предсказывает продолжение. За счёт обучения на большом корпусе текста модель умеет работать с языком, кодом и частью математических задач.

## Что такое агент

Агент - это не просто LLM-вызов. У агента есть роль, входные данные, состояние, правила, tools и место в общем flow.

В MathCheck AI Vision Agent только читает фото, Solver решает условие, Grader оценивает работу, Reviewer проверяет итог.

## Чем LLM отличается от агента

LLM - это модель.

Агент - это программный компонент вокруг модели. Он знает свою роль, получает нужный кусок state, может использовать tools и передаёт результат дальше по графу.

## Что означает B в названии модели

B означает billion, то есть миллиарды параметров. Например 4B - около 4 миллиардов параметров.

Это не гарантия качества. Более крупная модель обычно требует больше памяти и работает медленнее.

## Что такое галлюцинация

Это случай, когда модель уверенно генерирует факт, которого нет во входных данных или который неверен.

Для нашего проекта пример галлюцинации - Grader приписал ученику корень, которого нет в confirmed transcript.

Поэтому student facts извлекаются детерминированно из подтверждённого текста, а Solver проверяется verifier.

## Что такое контекстное окно

Это объём токенов, который модель может одновременно учитывать во входе и рабочем контексте.

Если окно слишком маленькое, часть длинного решения или инструкции может не поместиться. Если поставить очень большое окно, локальная модель будет требовать больше памяти и может работать медленнее.

## Почему четыре агента, а не одна модель

Если одной модели дать фото, решение ученика, критерии и просьбу выставить балл, невозможно понять, где возникла ошибка.

Мы разделили ответственность:

- Vision отвечает за чтение фото;
- Solver за независимый эталон;
- Grader за оценивание;
- Reviewer за финальную проверку.

## Почему flow последовательный

Этапы зависят друг от друга.

Grader нельзя запускать до получения и проверки эталона. Solver нельзя запускать до подтверждения OCR. Поэтому fan-out здесь не даёт пользы.

## Какие паттерны мультиагентных систем рассматривались

Основные варианты:

- последовательный pipeline;
- router, который выбирает следующего агента;
- supervisor-worker;
- fan-out/fan-in;
- agent-to-agent conversation.

У нас последовательный pipeline с conditional routing, потому что порядок проверки известен заранее.

## Почему LangGraph

LangGraph хорошо подходит для stateful flow с узлами и условиями переходов.

Нам удобно явно показать:

- state;
- остановку на human confirmation;
- переходы между агентами;
- error branches.

## Почему не CrewAI

CrewAI удобен, когда агенты распределяют задачи по ролям и больше взаимодействуют как команда.

У нас строгая математическая цепочка, поэтому прозрачный state graph удобнее.

## Почему не AutoGen

AutoGen хорошо подходит для диалогов между агентами. В нашем случае свободный диалог только увеличил бы недетерминированность.

## Почему Ollama

Нужен локальный inference без платного внешнего API. Ollama легко запускается на Mac, умеет Vision и позволяет быстро переключать модели.

## Какие модели пробовали

Основные сравниваемые модели:

- qwen3-vl:4b-instruct;
- gemma3:4b;
- granite3.2-vision:2b.

Дополнительно пробовали qwen2.5vl:7b и qwen3-vl:4b, но на нашей локальной конфигурации у них были проблемы с Vision stream.

## Почему выбрали qwen3-vl:4b-instruct

На нашем Vision benchmark она единственная стабильно прошла все 10 кейсов с valid JSON rate 1.0.

У неё не идеальный OCR, поэтому human confirmation оставлен обязательным.

## Что такое skills

Skill - отдельная инструкция под конкретную функцию агента.

Например `skills/task_13/solve.md` говорит Solver, что именно важно получить для №13 и какие machine-readable данные вернуть verifier.

Skill отличается от system prompt тем, что system prompt описывает постоянную роль агента, а skill добавляет правила конкретной задачи.

## Какие tools используются

Основные tools:

- parser;
- preflight;
- SymPy;
- reference verifier;
- проверка корней;
- rubric;
- SQLite;
- report builder.

## Зачем SymPy, если есть LLM

LLM может ошибиться даже в ответе, который выглядит убедительно.

Там, где математику можно проверить кодом, лучше сделать независимую проверку. Поэтому Solver предлагает эталон, а verifier проверяет его.

## Как устроена краткосрочная память

`ReviewState` хранит состояние одной текущей проверки.

Там находятся OCR, confirmed transcript, reference, результаты Grader и Reviewer, timings и другие поля.

## Как устроена долгосрочная память

SQLite хранит прошлые review по `student_id` и `review_id`.

## Почему не обычный RAG

Нам в основном нужны точные структурированные данные.

Вопрос "какой был последний балл ученика" лучше решается SQL-запросом, а не поиском похожего текста через embeddings.

Критерии №13 маленькие и заранее известны, поэтому их проще хранить в Git.

## Какие memory варианты рассматривались

Рассматривались SQLite, vector RAG, Graphiti, PageIndex, Mem0, LangMem, Cognee, Letta, LlamaIndex и другие варианты из ТЗ.

Для MVP SQLite проще, точнее и легче объясняется.

## Минус SQLite

Нет semantic search и автоматического связывания похожих ошибок между разными работами.

Если проект станет большим, можно оставить SQLite для точных фактов и добавить Graphiti или LangMem для более сложной персональной памяти.

## Почему нужен Docker

Docker изолирует Python-приложение, зависимости и файловую среду. Другой человек может поднять тот же Agent App без ручной установки каждой библиотеки.

## Почему Ollama не обязательно внутри того же контейнера

На Mac Ollama удобно оставить на host, чтобы использовать локальное аппаратное ускорение. Agent App при этом работает в Docker и обращается к host Ollama по API.

## Какие варианты изоляции рассматривались

- venv;
- Docker;
- VM;
- sandbox/microVM.

VM и microVM для текущего проекта избыточны, потому что система не исполняет недоверенный пользовательский код.

## Что такое evals

Evals - повторяемые тесты качества модели и системы на фиксированном наборе примеров.

У нас отдельно оценивается Vision и отдельно grading после human confirmation.

## Почему Vision и SYSTEM benchmark разделены

Если прогнать весь pipeline от фото и получить неправильный балл, непонятно, виноват OCR или Grader.

Разделение позволяет измерить два разных качества:

- как модель читает фото;
- как система проверяет уже подтверждённый текст.

## Какие метрики есть у Vision

- success rate;
- valid JSON rate;
- OCR similarity;
- human correction rate;
- latency.

## Какие метрики есть у grading

- score accuracy;
- mean absolute score error;
- reference success rate;
- manual review rate;
- false error rate;
- latency по этапам.

## Что показал основной benchmark

После human confirmation итоговый score совпал с экспертным в 9 из 10 случаев.

Score accuracy = 0.90.

Reference success rate = 1.00.

## Почему один кейс не совпал

В `13.1.2` экспертный балл учитывал ошибку ученика в визуальном отборе на окружности.

Текущий MVP ученическую окружность не оценивает. Он проверяет confirmed transcript и выбранные корни.

## Что такое observability

Это возможность понять, что происходило внутри системы во время запуска.

У нас есть:

- logs;
- metrics;
- traces;
- alerts.

## Где хранятся логи

Локально в JSONL.

Основные файлы:

```text
llm_calls.jsonl
traces.jsonl
alerts.jsonl
```

## Что такое trace

Trace - полный путь одной проверки по этапам.

`review_id` используется как `trace_id`. У каждого этапа есть отдельный span с временем начала, конца, статусом и duration.

## Какие алерты есть

Если LLM-вызов работает дольше установленного порога, пишется `slow_llm_call`.

## Почему не LangSmith или Langfuse

Они рассматривались и подходят для более крупного проекта.

Для локального учебного MVP простой JSONL tracing легче запустить, он не требует отдельного сервиса и API key.

## Главный риск проекта

Vision OCR.

Даже лучшая из протестированных локальных моделей ошибалась в рукописной математике. Поэтому OCR нельзя автоматически считать правильным.

## Почему human confirmation не костыль

Это архитектурная граница доверия.

Пользователь подтверждает, что система действительно прочитала работу ученика правильно. После этого математические агенты работают уже с подтверждёнными данными.

## Что бы улучшили дальше

Если продолжать проект:

1. ускорить inference;
2. расширить dataset;
3. добавить другие задания ЕГЭ;
4. улучшить Vision OCR;
5. при росте системы подключить Langfuse или OpenTelemetry;
6. добавить более сложную персональную память только когда она реально понадобится.
