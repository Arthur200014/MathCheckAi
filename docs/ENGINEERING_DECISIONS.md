# Engineering decisions — MathCheck AI

Этот файл фиксирует варианты, которые рассматривались для учебного MVP ЕГЭ №13, и причину выбора. Это не рейтинг технологий вообще: решение относится к нашему локальному однопользовательскому проекту на Mac.

## Agent framework

| Вариант | Для нашего проекта | Решение |
|---|---|---|
| LangGraph | Явный state, узлы, conditional edges; удобно показать последовательность Vision → Solver → Grader → Reviewer и остановку на human confirmation | **Выбран** |
| CrewAI | Удобен для role-based команд агентов, но наш flow фиксированный и нам важнее прозрачный state/graph, чем автономное распределение задач | Рассмотрен |
| AutoGen | Силен в agent-to-agent conversation, но для нашего проверочного pipeline свободный диалог агентов добавил бы лишнюю недетерминированность | Рассмотрен |
| Самописный orchestrator | Минимум зависимостей, но сложнее убедительно показать использование agent framework по ТЗ и поддерживать graph/state | Не выбран |

Почему LangGraph: архитектура задачи уже является конечным графом с чёткими переходами, human gate и shared `ReviewState`. Нам не нужен агент, который сам придумывает следующий шаг.

## Inference engine

| Вариант | Для нашего проекта | Решение |
|---|---|---|
| Ollama | Простой локальный запуск open-weight моделей, Vision input, API, удобная смена модели через env | **Выбран** |
| llama.cpp | Даёт много контроля над локальным inference/quantization, но потребовал бы больше собственной runtime-конфигурации для учебного MVP | Рассмотрен |
| vLLM | Ориентирован на высокопроизводительное serving и batching; для одного Mac и последовательного локального pipeline это лишняя инфраструктура | Рассмотрен |

Почему Ollama: нам важнее быстро и воспроизводимо переключать несколько локальных моделей для benchmark, чем максимальная серверная пропускная способность.

## Isolation

| Вариант | Для нашего проекта | Решение |
|---|---|---|
| Python venv | Удобен для разработки, но изолирует только Python-зависимости | Используется локально для разработки |
| Docker | Воспроизводимый Agent App, зависимости и файловая среда; легко показать на защите | **Выбран для сдаваемого app** |
| Полная VM | Сильнее изоляция, но тяжелее запуск/демо | Не выбрана |
| sandbox/microVM | Нужен в первую очередь при исполнении недоверенного пользовательского кода; MathCheck такого кода не выполняет | Избыточно для MVP |

На macOS FastAPI/LangGraph/tools/SQLite запускаются в Docker, а Ollama остаётся на host. Это позволяет контейнеризировать приложение, не усложняя доступ локальной модели к аппаратному ускорению.

## Memory: SQLite vs RAG/Graphiti/Mem0

| Вариант | Какая задача решается | Решение для MVP |
|---|---|---|
| SQLite | Точные структурированные review, score, status, история ученика | **Выбран** |
| Обычный vector RAG | Семантический поиск по большому неструктурированному корпусу | Не нужен как основная память |
| Graph-based memory / Graphiti-подобный подход | Связи сущностей и фактов во времени | Избыточно для простых review/history |
| Memory framework / Mem0-подобный подход | Автоматическое извлечение и поддержание пользовательских фактов | Избыточно и добавляет ещё один недетерминированный слой |

Почему простой RAG здесь не оптимален: вопрос `какой балл был у student-001 в последней проверке №13?` — структурированный SQL-запрос, а не поиск похожего текста. Критерии №13 также малы и version-controlled в репозитории, поэтому для них не нужен vector database.

## LLM vs deterministic tools

Мы намеренно не отдаём всю математику одной LLM.

- Vision нужен для чтения рукописного изображения.
- Solver нужен для независимого смыслового решения.
- SymPy/reference verifier проверяет семейства и корни там, где это можно сделать точно.
- Grader получает source-locked подтверждённое решение ученика.
- Итоговый rubric score вычисляется детерминированно.
- Reviewer только проверяет непротиворечивость и не может заменить score.

Это разделение уменьшает риск, что один красивый, но неверный LLM-ответ сразу станет итоговой оценкой.

## Sequential vs parallel execution

Solver → verifier → Grader → Reviewer имеют зависимости по данным, поэтому основной grading tail последовательный. Кроме того, на одном локальном ускорителе одновременный запуск нескольких крупных моделей конкурирует за общую память.

Независимые CPU tools можно было бы параллелить, но быстрый reference verifier теперь занимает малую долю общего latency, поэтому усложнение orchestration не даёт заметной экономии. Оптимизацию делаем по реальным stage timings и benchmark, а не добавлением параллелизма заранее.
