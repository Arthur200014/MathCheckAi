# Отчёт по проекту MathCheck AI

## 1. Что это за проект

MathCheck AI проверяет решение задания ЕГЭ №13 по фотографии.

Пользователь загружает одну или несколько фотографий одной работы. Сначала Vision Agent делает транскрипцию. Потом человек проверяет распознанный текст. Только после этого система решает задачу, сравнивает решение ученика с эталоном и формирует итоговый отчёт.

Текущий MVP поддерживает только задание №13.

## 2. Зачем нужна такая система

Проверка №13 состоит не только из проверки финального ответа. Нужно понять ход решения, проверить общее решение тригонометрического уравнения, отбор корней на отрезке и выставить 0, 1 или 2 балла по критериям.

Обычный процесс у преподавателя такой:

1. прочитать рукописное решение;
2. восстановить математическую запись;
3. решить задачу независимо;
4. сравнить решение ученика с эталоном;
5. проверить пункт б);
6. выставить балл;
7. написать комментарий.

MathCheck AI автоматизирует большую часть этой цепочки, но оставляет человеку контроль над OCR.

## 3. ТЗ на агента

Полное ТЗ лежит в `docs/TZ.md`.

Коротко требования такие:

- вход: фото работы ЕГЭ №13;
- OCR обязательно подтверждается человеком;
- решение ученика нельзя молча исправлять;
- Solver решает задачу независимо;
- эталон проверяется deterministic verifier;
- Grader работает по критериям;
- Reviewer проверяет итог;
- результат сохраняется;
- система пишет логи, метрики, трейсы и алерты;
- приложение должно запускаться локально и в Docker.

## 4. Архитектура

Основной flow последовательный:

```text
Фото
  -> Vision Agent
  -> Human confirmation
  -> Preflight
  -> Solver Agent
  -> Reference Verifier
  -> Grader Agent
  -> Reviewer Agent
  -> Report Builder
  -> SQLite
```

Последовательность выбрана потому, что каждый следующий этап зависит от предыдущего.

Vision должен сначала получить текст. Solver должен работать с подтверждённым условием. Grader не должен запускаться до проверки эталона.

### Почему это мультиагентная система

В проекте четыре LLM-агента с разными ролями.

**Vision Agent**

Читает фото. Не решает задачу и не исправляет ученика.

**Solver Agent**

Получает условие и строит независимый эталон. Решение ученика ему не передаётся.

**Grader Agent**

Сопоставляет подтверждённое решение ученика с эталоном и критериями.

**Reviewer Agent**

Проверяет непротиворечивость результата и отмечает случаи для ручной проверки.

Все агенты входят в один LangGraph flow и работают с общим `ReviewState`.

C4 схема находится в `docs/C4.md`, sequence diagram находится в `docs/sequence.mmd`.

## 5. Почему LangGraph

Рассматривались LangGraph, CrewAI, AutoGen и обычный самописный pipeline.

Для проекта выбран LangGraph, потому что у нас не свободный чат агентов, а понятная цепочка с состоянием и условиями перехода.

Нам нужны:

- общий state;
- остановка после OCR;
- продолжение после подтверждения;
- условные переходы;
- понятный порядок узлов.

CrewAI больше подходит для команд агентов с role-based взаимодействием. AutoGen хорошо подходит для диалога агентов. В нашем случае это добавило бы лишнюю недетерминированность.

## 6. Движок LLM

Рассматривались:

- Ollama;
- llama.cpp;
- vLLM.

Выбран Ollama.

Причины:

- простой локальный запуск;
- есть API;
- удобно менять модели;
- можно запускать Vision models;
- подходит для одного Mac;
- не нужно поднимать отдельный GPU server.

vLLM имеет смысл при серверном inference и большом количестве параллельных запросов. llama.cpp даёт больше низкоуровневого контроля, но требует больше ручной настройки.

## 7. Выбор LLM

Подробности находятся в `docs/LLM_SELECTION.md`.

В локальных тестах использовались:

- `qwen3-vl:4b-instruct`;
- `gemma3:4b`;
- `granite3.2-vision:2b`;
- дополнительно `qwen2.5vl:7b`;
- дополнительно `qwen3-vl:4b`.

### Vision сравнение

| Модель | Объём | Vision success | Valid JSON | OCR similarity | Среднее время |
|---|---:|---:|---:|---:|---:|
| qwen3-vl:4b-instruct | 10 | 1.000 | 1.000 | 0.268 | 286.32 s |
| gemma3:4b | 8 завершённых | 0.375 | 0.375 | 0.132* | 240.68 s |
| granite3.2-vision:2b | 3 завершённых | 0.333 | 0.333 | 0.008* | 296.63 s |
| qwen2.5vl:7b | 10 | 0.000 | 0.000 | нет | 12.76 s |
| qwen3-vl:4b | 10 | 0.000 | 0.000 | нет | 13.67 s |

`*` Similarity посчитана только по успешным ответам.

Основной моделью оставлена `qwen3-vl:4b-instruct`.

Главная причина не в том, что у неё идеальный OCR. Он не идеальный. Но эта модель единственная стабильно завершила все 10 Vision-кейсов и вернула валидный structured output на всех 10.

Gemma и Granite на части кейсов уходили в повторяющуюся генерацию и ломали JSON. Это тоже важный критерий для agentic system, потому что агент должен соблюдать контракт вызова.

Для короткой проверки математической точности, hallucination и role following добавлен `evals/run_model_selection.py`.

## 8. Prompts и skills

System prompts вынесены отдельно:

```text
prompts/vision_agent.md
prompts/solver_agent.md
prompts/grader_agent.md
prompts/reviewer_agent.md
```

Skills тоже лежат отдельными файлами:

```text
skills/common/transcribe_math_solution.md
skills/common/solve_task.md
skills/common/review_feedback.md
skills/task_13/solve.md
skills/task_13/grade.md
```

Skill задаёт конкретный способ работы агента в рамках задачи. Например, Solver skill описывает, что нужно получить в решении №13 и какие данные вернуть verifier.

Постоянные правила системы лежат в `knowledge/`. Главный файл принципов - `knowledge/SOUL.md`.

## 9. Tools

Часть логики специально вынесена из LLM.

Используются:

- parser школьной математической записи;
- preflight;
- SymPy;
- reference verifier;
- проверка семейств корней;
- проверка корней на отрезке;
- rubric;
- report builder;
- SQLite persistence.

Это сделано потому, что точные математические проверки лучше выполнять кодом там, где это возможно.

Например, красивый ответ Solver не считается правильным только потому, что модель уверена. Сначала reference verifier проверяет его.

## 10. Память

Подробное описание находится в `docs/MEMORY.md`.

В проекте три уровня.

### Краткосрочная память

`ReviewState` хранит данные одной текущей проверки.

### Долгосрочная память

SQLite хранит историю review:

- student id;
- review id;
- score;
- status;
- error class;
- JSON результата;
- дату.

### Постоянные знания

Критерии, skills и правила лежат в `.md` и `.json` файлах репозитория.

### Почему не RAG

Основные данные проекта структурированы. Чтобы узнать последний балл ученика, точный SQL запрос лучше semantic search.

Критерии №13 небольшие и заранее известны. Их проще хранить в Git рядом с кодом.

Также были рассмотрены Graphiti, PageIndex, SuperMemory, Cognee, Letta, LangMem, memU, Mem0, LlamaIndex, Zep и RAGFlow. Для текущего MVP они дают больше сложности, чем пользы.

## 11. Изоляция

Рассматривались:

- Python venv;
- Docker;
- VM;
- sandbox или microVM.

Для разработки используется venv. Для сдаваемого приложения выбран Docker.

На macOS приложение запускается в контейнере, а Ollama можно оставить на host. Это удобно, потому что модель использует локальное аппаратное ускорение, а Python приложение остаётся в воспроизводимой среде.

Полная VM для такого MVP слишком тяжёлая. Отдельный sandbox особенно полезен, если агент исполняет недоверенный пользовательский код. MathCheck AI пользовательский код не запускает.

## 12. Evals

Оценка специально разделена на две части.

### Vision benchmark

Проверяет:

```text
Photo -> Vision Agent -> OCR -> comparison with manual transcript
```

Метрики:

- Vision success rate;
- valid JSON rate;
- OCR similarity;
- latency;
- human correction rate.

Результат основной модели на 10 фото:

- Vision success rate: 1.00;
- valid JSON rate: 1.00;
- mean OCR similarity: 0.268;
- human correction rate: 1.00;
- average Vision time: 286.32 s.

Human correction rate 1.00 показывает, что обязательное подтверждение OCR нужно оставлять в архитектуре.

### SYSTEM benchmark

Проверяет математическую часть после human confirmation:

```text
Confirmed transcript
  -> Solver
  -> Reference Verifier
  -> Grader
  -> Reviewer
  -> score vs expert
```

Результат на 10 кейсах:

- score accuracy: 0.90;
- mean absolute score error: 0.10;
- reference success rate: 1.00;
- manual review rate: 0.10;
- false error rate на expert=2: 0.00;
- positive score rate на expert=0: 0.00;
- average total time: 166.97 s.

Одно несовпадение было на `13.1.2`. Экспертный балл там связан с визуальной ошибкой на окружности. В текущем MVP ученическая окружность не оценивается.

Все подробные результаты лежат в `docs/EVAL_RESULTS_SUMMARY.md`.

## 13. Observability

В проекте есть четыре части наблюдаемости.

### Логи

LLM вызовы сохраняются в `llm_calls.jsonl`.

### Метрики

Сохраняются timings этапов, количество успешных проверок, manual review rate, ошибки и LLM telemetry.

### Трейсы

Каждый LangGraph этап пишет span в `traces.jsonl`.

Для span есть:

- trace id;
- span id;
- stage;
- start;
- end;
- duration;
- status;
- error.

Один `review_id` используется как trace id, поэтому можно собрать путь одной проверки по этапам.

### Алерты

Если LLM вызов дольше заданного порога, событие попадает в `alerts.jsonl` как `slow_llm_call`.

По умолчанию порог 120 секунд.

### Почему не LangSmith

LangSmith и Langfuse рассматривались. Для текущего локального MVP выбран простой JSONL вариант без внешних ключей и сервисов.

Если проект станет больше, эти события можно отправлять в Langfuse, LangSmith или OpenTelemetry.

## 14. Основные проблемы во время разработки

### OCR ошибается на рукописной математике

Решение: обязательный human confirmation.

### LLM может вернуть правдоподобный, но неверный эталон

Решение: отдельный deterministic verifier.

### Локальные Vision модели очень медленные

Решение: один Vision pass на работу, несколько фото объединяются перед распознаванием, отдельная проверка ученической окружности убрана из MVP.

### Модель может сломать JSON

Решение: response schema, ограничение генерации и строгая проверка финального ответа.

### Ollama stream иногда обрывается

Решение: transport обрабатывает incomplete stream как ошибку, а не как успешный OCR.

## 15. Что сознательно не входит в MVP

- другие задания ЕГЭ;
- автоматическая оценка нарисованной учеником тригонометрической окружности;
- облачный inference;
- vector database;
- сложная персональная memory system;
- автоматическое принятие OCR без человека.

## 17. Итог

В проекте получился рабочий MVP одной конкретной задачи, а не набор отдельных агентов.

Есть единый LangGraph flow, четыре LLM-агента, deterministic tools, human confirmation, Docker, память, evals и observability.

Основная математическая часть после подтверждения OCR совпала с экспертным баллом в 90% случаев на измеренном наборе. Главным ограничением остаётся Vision: рукописную математику локальные небольшие модели читают заметно хуже, поэтому OCR нельзя автоматически считать истиной.
