# Evals для ЕГЭ №13

Здесь лежит воспроизводимый benchmark для сдачи проекта. Цель — не написать «мы пробовали три модели», а получить реальные цифры на одном и том же наборе экспертно оценённых работ и не смешать ошибки OCR с качеством последующей проверки.

## Что именно тестируем

Основной benchmark повторяет реальный flow MathCheck AI:

1. фото попадает в Vision Agent;
2. сырой OCR сравнивается с эталонной транскрипцией — это отдельная метрика качества распознавания;
3. в точке обязательного human confirmation используется проверенная транскрипция так же, как пользователь исправляет текст в редакторе сайта;
4. запускаются Solver → deterministic reference verifier → Grader → Reviewer;
5. итоговый балл сравнивается с экспертным баллом.

Это один benchmark, а не два разных продукта. Raw OCR не выдаётся Grader как подтверждённый текст: в реальном интерфейсе между Vision и оцениванием есть обязательное подтверждение пользователя.

Время ручного редактирования не включается в latency моделей. Отдельно считаются Vision / Solver / Grader / Reviewer и суммарное машинное время.

## Набор

`task_13/benchmark_cases.json` содержит 12 сбалансированных кейсов:

- 4 работы на 2 балла;
- 4 работы на 1 балл;
- 4 работы на 0 баллов.

Для каждого кейса хранятся:

- рукописное изображение;
- условие и интервал;
- `manual_transcript` — транскрипция для сравнения OCR и для точки human confirmation;
- экспертный балл и комментарий;
- ожидаемые ключевые шаги;
- ожидаемые ошибки;
- ожидаемая необходимость ручной проверки.

Экспертные баллы и комментарии взяты из `sources/ЕГЭ_13_критерии_решения_сканы.pdf`.

Перед финальным benchmark транскрипции нужно один раз визуально сверить с исходными сканами. Это ground truth: его нельзя автоматически «улучшать» моделью после того, как увидели результат benchmark.

Для Vision нельзя отправлять всю страницу PDF: сверху напечатан официальный ответ, снизу — комментарий и балл эксперта. Поэтому `prepare_ege13_images.py` оставляет только рукописную часть. Crop-координаты зафиксированы в JSON, чтобы все модели получали одинаковые изображения.

## 1. Подготовить изображения

```bash
pip install -r requirements-eval.txt
python evals/prepare_ege13_images.py
```

Получится `local_eval_data/` с PNG. Папка gitignored и не попадает в репозиторий.

Перед benchmark быстро открой несколько PNG и проверь, что в crop не попали печатный официальный ответ и комментарий эксперта.

## 2. Быстрый пробный benchmark

Сначала проверяем один кейс на уже установленной основной модели:

```bash
python evals/run_ege13_benchmark.py --models qwen3-vl:4b-instruct --limit 1
```

В начале должно быть явно напечатано:

```text
Flow: Vision -> human confirmation (ground truth) -> Solver -> verifier -> Grader -> Reviewer
```

Для кейса вывод содержит и итоговый балл, и OCR similarity.

После того как один кейс корректно проходит весь flow, можно проверить один и тот же кейс на всех трёх моделях:

```bash
python evals/run_ege13_benchmark.py --limit 1
```

Модели по умолчанию берутся из `src/llm/config.py`:

- `qwen3-vl:4b-instruct`;
- `qwen2.5-vl:7b`;
- `granite3.2-vision:2b`.

Если модель ещё не установлена в Ollama, сначала скачай её через `ollama pull ...`.

## 3. Финальный benchmark

После визуальной проверки ground truth и пробного запуска:

```bash
python evals/run_ege13_benchmark.py
```

Для каждой пары `модель × работа` сохраняются сырой текст Vision и подтверждённая транскрипция. Это позволяет по любому ошибочному баллу понять, на каком слое возникла проблема.

Результаты сохраняются в `evals/results/` одновременно как JSON, CSV и Markdown.

## Метрики

Основные метрики для отчёта:

- `mean_vision_similarity` — похожесть сырой транскрипции Vision на ground truth;
- `human_correction_rate` — доля работ, где OCR пришлось бы поправить перед оцениванием;
- `score_accuracy` — доля точных совпадений итогового балла с экспертом после предусмотренного human confirmation;
- `mean_abs_score_error` — средняя абсолютная ошибка балла;
- `vision_success_rate`;
- `reference_success_rate`;
- `manual_review_rate`;
- `manual_review_match_rate` — совпала ли необходимость ручной проверки с разметкой кейса;
- latency Vision / Solver / Grader / Reviewer / общего машинного flow;
- `false_error_rate_on_expert_2` — эксперт дал 2, а система дала меньше;
- `positive_score_rate_on_expert_0` — эксперт дал 0, а система дала положительный балл.

Math-step coverage и hallucination rate считаются по `expected_key_points` / `expected_errors`; эти поля хранятся в dataset и должны использоваться при финальном разборе результатов.
